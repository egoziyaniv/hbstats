1. תקציר מנהלים

בוצעה סקירת עומק (read-only) של פלטפורמת StatsAI לקראת עלייה לפרודקשן: ארכיטקטורה, הזדהות והרשאות, אבטחת API, בסיס נתונים, פרונטאנד, אפליקציית מובייל, סודות, תלויות, לוגים ולוגיקת הסטטיסטיקות עצמה.

השורה התחתונה: יסודות האבטחה הקלאסיים חזקים באופן יוצא דופן לפרויקט בסדר הגודל הזה — אין דליפת סודות, אין XSS, אין IDOR, וכל ממשקי האדמין מוגנים בצד השרת. מה שחוסם עלייה הוא שלמות נתונים ותפעול: באג חמור שמשחית סטטיסטיקות שחקנים, מחיקה שקטה של נתונים ממוזגים, היעדר גיבויים, וארכיטקטורת דפים שמחשבת 26 שנות נתונים בכל בקשה.

✅ מה שנמצא חזק (לשמר)

  • הזדהות: bcrypt(12), טוקני סשן אקראיים נשמרים כ-hash בלבד, ביטול כל הסשנים בשינוי סיסמה, refresh-rotation עם זיהוי שימוש חוזר (family revocation).
  • הרשאות: כל 21 נתיבי האדמין אומתו — בדיקת role בצד השרת. אפס IDOR. אפס mass-assignment (רשימות שדות מפורשות בכל עדכון).
  • סודות: היסטוריית Git נקייה לחלוטין (392 קומיטים נסרקו) — אף מפתח אמיתי לא הוזרק מעולם. CI כולל סריקת סודות ל-bundle המובייל.
  • XSS: אפס שימוש מסוכן ב-HTML — כל תוכן דינמי (חדשות טלגרם, תשובות AI, שמות מ-scraping) מרונדר כטקסט מוגן React.
  • מובייל: ארכיטקטורת טוקנים מדויקת — refresh ב-Keychain בלבד, access בזיכרון בלבד, ATS מלא, אפס לוגים רגישים.
  • ארכיטקטורת מיזוג: מודל staging → preview → approve → execute → rollback הוא העיצוב הנכון; הפערים בביצוע, לא בתפיסה.

2. ארבעת הממצאים הקריטיים — פירוט

C-1 · עריכת אירוע משחק משחיתה סטטיסטיקות קריירה CRITICAL

מיקום: src/app/api/events/route.ts:21-45

הפונקציה buildStatDelta מחזירה { goals: 1 } (ערך מוחלט) במקום { goals: { increment: 1 } } — Prisma מציב 1 במקום להוסיף 1. חמור מכך: ה-where הוא { playerId } בלבד, ללא עונה/מסגרת — כלומר העדכון פוגע בכל שורות הסטטיסטיקה של השחקן, בכל העונות.

משמעות: הוספת שער אחד דרך עורך המשחקים מאפסת מלך שערים היסטורי ל-1 שער בכל עונה. מחיקת אירוע מציבה 1-. כל עריכת אירוע מאז שהקוד עלה גרמה נזק שקט.

טיפול: (1) תיקון ל-increment + צמצום ה-where לעונה ולמסגרת של המשחק. (2) ביקורת נזק: SELECT * FROM player_statistics WHERE goals < 0 + השוואה מול מקורות הגלם ושחזור. מאמץ: ~10 שורות קוד + חצי יום ביקורת נזק.

C-2 · משיכת שחקנים חוזרת מוחקת שחקנים ממוזגים וכל הסטטיסטיקות שלהם CRITICAL

מיקום: src/app/api/admin/fetch/route.ts:1636-1661

בסוף סנכרון שחקנים מ-API-Football רץ player.deleteMany שמוחק כל שחקן עם apiFootballId = null ששמו האנגלי אינו ברשימת ה-API. שחקנים שנוצרו ממיזוג IFA מקבלים שם עברי בשדה nameEn — הם לעולם לא ברשימה, ולכן נמחקים יחד עם הסטטיסטיקות שלהם (cascade). עיקרון "מיזוג לא מוחק לעולם" נשבר במסלול ה-fetch.

משמעות: פעולת אדמין שגרתית (רענון סגל) משמידה בשקט נתונים סרוקים שאין להם תחליף.

טיפול: צמצום המחיקה לשחקנים עם apiFootballId ≠ null בלבד, או תיוג מקור (source) לכל שחקן. מאמץ: ~5 שורות.

C-3 · אין גיבויים אוטומטיים CRITICAL

מיקום: אין — זו הבעיה. נבדקו scripts/, crontab ותיעוד הפריסה.

26 עונות של נתונים (~13K משחקים, ~208K הרכבים, ~122K אירועים) שעלות שחזורם היא חודשי scraping — קיימים בעותק יחיד על דיסק יחיד בשרת יחיד. הייצוא הידני מהאדמין אינו תחליף.

טיפול: cron לילי: pg_dump -Fc → רוטציה 7/30 יום → עותק מחוץ לשרת (Hetzner Storage Box / S3). לבצע תרגול שחזור אחד. מאמץ: ~שעה.

C-4 · ייבוא DB מהאדמין: מחיקת הכל לפני שחזור, ללא רשת ביטחון CRITICAL

מיקום: src/app/api/admin/db-transfer/route.ts:113-140

הייבוא מוחק את כל הטבלאות (DROP CASCADE, שגיאות נבלעות) ואז משחזר. כשל זיהוי שגיאות (רק "FATAL" ב-stderr נחשב כישלון), הקובץ כולו נטען לזיכרון ללא הגבלת גודל (סכנת OOM על שרת 3GB = השבתה באמצע DROP), וקובץ פגום משמיד את ה-DB ללא דרך חזרה.

טיפול: snapshot אוטומטי לפני DROP, בדיקת גודל קובץ, שחזור לסכמה זמנית והחלפה אטומית, כשל על exit code. מאמץ: חצי יום.

7. בדיקות שמומלץ להוסיף

  1. בדיקות golden-file ל-matchTeamName/normalizeName — מפת הקיצורים היא תשתית קריטית לשלמות הנתונים
  2. בדיקת round-trip למנוע המיזוג: preview → execute → rollback על נתוני fixture, כולל תרחיש "DB השתנה בין preview ל-execute"
  3. בדיקת נכונות stat-delta ב-API האירועים — assertion אחד היה תופס את C-1
  4. מיון טבלה: pointsAdjustment + קבוצות פלייאוף
  5. אידמפוטנטיות fetch: אותה עונה פעמיים → אפס שורות חדשות
  6. מטריצת CSRF ב-middleware: origin מדויק, התקפת prefix, origin חסר
  7. מובייל: logout מנקה cache; ה-persister לא שומר שאילתות עם נתוני משתמש

8. החלטה: Go / No-Go

NO-GO כרגע — אך ורק בגלל C-1 עד C-4 (השחתת נתונים פעילה + היעדר רשת ביטחון). מדובר בימים, לא בחודשים: תיקון C-1 הוא ~10 שורות, C-2 ~5 שורות, גיבויים — cron אחד.

הארכיטקטורה עצמה — staging→preview→rollback, סטטיסטיקות בצד שרת, auth נקי — היא היסוד הנכון ואינה דורשת בנייה מחדש. עם סגירת שלב 0 ושלב 1: GO.
