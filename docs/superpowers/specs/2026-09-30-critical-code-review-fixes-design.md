## מטרות

1. ייבוא בסיס נתונים לא יתקדם לשחזור אם הכנת בסיס הנתונים נכשלה.
2. Rollback של מיזוג לא ידרוס נתונים ששונו אחרי המיזוג.
3. Rollback יסתיים כולו או לא ישנה דבר, והסטטוס ישקף את התוצאה האמיתית.
4. קישור איפוס סיסמה יוכל לשנות סיסמה פעם אחת בלבד, גם בבקשות מקבילות.

## מחוץ לתחום

- אין שינוי בפורמט קובצי הגיבוי או בזרימת האישור הקיימת באדמין.

## P0-1 — שחזור בסיס נתונים

### התנהגות נדרשת

זרימת הייבוא תישאר: אימות קובץ → snapshot → מחיקת טבלאות → restore. כל קריאת `runPg` היא שער מחייב: רק `code === 0` מאפשר להתקדם.

- כישלון ביצירת snapshot משאיר את מסד הנתונים ללא שינוי ועוצר את הייבוא.
- כישלון במחיקת הטבלאות הראשונית לא מפעיל restore של הקובץ המיובא. ה־snapshot נשמר והתגובה מציינת שנדרשת בדיקה ידנית.
- כישלון ב־restore מפעיל rollback אוטומטי כבעבר.
- לפני rollback נבדקת מחיקת הטבלאות. אם היא נכשלת, לא מפעילים `pg_restore` על מצב לא ידוע; ה־snapshot נשמר ומוחזרת דרישה להתערבות ידנית.
- כישלון ב־rollback שומר את ה־snapshot ומדווח `rolledBack: false`.
- snapshot נמחק רק לאחר restore מוצלח או rollback מוצלח.

### מבנה הקוד

תתווסף בדיקה מפורשת לתוצאת שתי קריאות המחיקה. הודעות השרת יכללו את `stderr` בלוג בלבד, בעוד תגובות ה־API יישארו כלליות בעברית ולא יחשפו פרטי חיבור.

### בדיקות

- כשל במחיקה הראשונית מונע קריאת restore ומשאיר snapshot.
- כשל במחיקה שלפני rollback מונע קריאת `pg_restore`, מחזיר 500 ומשאיר snapshot.
- המסלול המוצלח הקיים ממשיך למחוק snapshot זמני.

## P0-2 ו־P0-3 — Rollback בטוח ואטומי למיזוג

### חוזה הפעולה

`rollbackMerge` ירוץ בתוך interactive transaction יחידה עם רמת בידוד `Serializable` וזמן פעולה מוגדל שמתאים למיזוגים היסטוריים. בתוך העסקה יתבצעו השלבים הבאים:

1. claim אטומי של `MergeOperation` מ־`executed` ל־`rolling_back` באמצעות `updateMany` מותנה.
2. טעינת `snapshotJson` ו־`changesJson` מתוך אותה עסקה.
3. בדיקת כל הרשומות לפני שינוי כלשהו.
4. ביצוע כל השחזורים והמחיקות בסדר תלות בטוח.
5. שינוי הסטטוס ל־`rolled_back` וקביעת `rolledBackAt` רק לאחר שכל הפעולות הצליחו.

אם בדיקה או כתיבה נכשלת, נזרקת שגיאה והעסקה כולה מתבטלת. גם ה־claim מתבטל ולכן הסטטוס נשאר `executed`, בלי `rolledBackAt` ובלי נתונים ששוחזרו חלקית.

### הגנת שינויים מאוחרים

לכל snapshot מסוג `update` ייגזרו הערכים שהמיזוג כתב מתוך `changesJson.applied`. לפני השחזור תיטען הרשומה הנוכחית ותושווה רק בשדות שהמיזוג שינה:

- אם כל הערכים עדיין שווים לערכי המיזוג, אפשר להחזיר את `snapshot.original`.
- אם שדה כלשהו שונה, הפעולה נעצרת עם הודעה שמזהה entity ו־id. הערך המאוחר נשמר.
- השוואת ערכי `Date`, מספרים, `null` ומחרוזות תעבור דרך נרמול משותף כדי למנוע סתירה מדומה בין ייצוגי JSON ו־Prisma.
- שדות מטא שמתחילים ב־`_` אינם נחשבים שדות DB.

לרשומות מסוג `create` נשמרת ההגנה הקיימת מפני מחיקת children שנוספו מאוחר יותר, אבל כל סתירה הופכת לכשל של כל העסקה במקום להצטבר במערך `errors`. אירועים והרכבים שנוצרו במיזוג יימחקו רק אם תוכנם עדיין תואם ל־snapshot. רשומות אב כגון משחק, קבוצה ועונה יימחקו רק כאשר אין להן נתונים מאוחרים.

### תאימות לנתונים היסטוריים

הפענוח יתמוך בשני ייצוגי `changesJson.applied` הקיימים:

- ערך ישיר, לדוגמה `{ goals: 4 }`.
- ערך preview, לדוגמה `{ goals: { old: 2, new: 4 } }`.

כך ניתן לבצע rollback בטוח גם למיזוגים שנוצרו לפני התיקון, בלי migration ובלי שינוי schema.

### תגובת API וממשק

- הצלחה תחזיר `{ success: true, reverted, errors: [] }`.
- סתירה או כשל יחזירו 500 דרך המסלול הקיים, עם הודעה בטוחה וברורה למנהל.
- אין סטטוס הצלחה חלקי. `rolling_back` הוא מצב פנימי בתוך העסקה ואינו אמור להישאר שמור לאחר כשל.
- ניקוי cache יתבצע רק אחרי commit מוצלח.

### בדיקות

- שינוי מאוחר בשדה שמיזוג עדכן גורם לכשל; השינוי נשמר וכל שאר הרשומות נשארות כפי שהיו.
- כשל לאחר שחזור רשומה אחת מבטל גם את השחזור שלה.
- שתי קריאות rollback מקבילות: אחת בלבד מצליחה והשנייה נדחית לפי הסטטוס.
- child שנוסף אחרי המיזוג מונע מחיקת האב ומבטל את כל ה־rollback.
- rollback מוצלח מסמן `rolled_back`, קובע זמן ומנקה cache.
- תמיכה בשני פורמטי `applied` נבדקת ביחידות.

## P0-4 — צריכה חד־פעמית של אסימון איפוס סיסמה

### התנהגות נדרשת

חישוב hash הסיסמה יישאר מחוץ לעסקה כדי לא להחזיק נעילה בזמן bcrypt. כל פעולת הנתונים תעבור ל־interactive transaction אחת:

1. טעינת האסימון לפי hash בתוך העסקה.
2. בדיקת `usedAt` ו־`expiresAt` בתוך העסקה.
3. נעילת רשומת המשתמש כדי לסדר גם ניסיונות דרך שני אסימונים שונים של אותו משתמש.
4. claim מותנה באמצעות `updateMany` לפי `id`, `usedAt: null` ו־`expiresAt > now`.
5. רק כאשר `count === 1`: עדכון סיסמה ו־`passwordChangedAt`, מחיקת sessions, וביטול שאר אסימוני האיפוס הפתוחים.

אם ה־claim מחזיר אפס, העסקה אינה משנה את המשתמש והתגובה זהה לקישור פג תוקף או מנוצל. רישום הפעילות יתבצע רק לאחר commit מוצלח.

### בדיקות

- שתי בקשות מקבילות עם אותו אסימון: אחת מחזירה 200 ואחת 400.
- רק הסיסמה מהבקשה המצליחה מתקבלת לאחר מכן.
- בקשה שנייה אינה מעדכנת `passwordChangedAt` ואינה יוצרת פעילות הצלחה.
- אסימון שפג תוקף ואסימון שכבר נוצל נשארים במסלול השגיאה הקיים.
- איפוס מוצלח ממשיך למחוק את כל ה־sessions ולבטל אסימונים פתוחים אחרים.

## שיטת יישום ואימות

העבודה תתבצע ב־TDD לכל גבול פעולה:

1. הוספת בדיקה שמדגימה את הכשל הנוכחי ואימות שהיא נכשלת מהסיבה הצפויה.
2. שינוי מינימלי בקוד עד שהבדיקה עוברת.
3. הרצת הבדיקות הממוקדות של DB transfer, merge rollback ו־password reset.
4. הרצת כלל בדיקות Jest, בדיקת TypeScript ו־build.
5. עדכון `APP_VERSION` ו־`package.json` באותה גרסת patch לפני push, בהתאם ל־`AGENTS.md`.
